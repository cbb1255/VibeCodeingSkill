# vibe-code — 从想法到交付的开发编排器

面向 Claude Code / Cowork 的开发编排 Skill。阶段 0 准备项目规则与基线，阶段 1–8 从产品方案走到用户亲自体验和授权交付。各阶段的执行条件见 [SKILL.md](SKILL.md)。

## 它解决什么问题

vibe coding 最常见的三个翻车点：

1. **需求没想清就开写** → 写到一半发现做的是错的东西
2. **范围不断膨胀** → 越做越大，永远做不完
3. **改错了退不回去** → 一改崩，没有回头路

vibe-code 用项目规则、三道文档验收、检查点和验证门禁来控制范围与交付质量。

## 核心机制

| 机制 | 说明 |
|---|---|
| **阶段 0–8** | 项目规则与基线 → 需求与产品方案 → 技术方案 → 验收标准 → 拆任务 → 实现与自测 → 正式评分 → 代码审查 → 人工体验与交付 |
| **项目规则与续接** | 阶段 0 核对并补齐适用规则，用规则文件保存长期约定并指向 `docs/vibe/state.md`。新会话重读规则、进度和下一动作 |
| **三道文档门禁** | 阶段 1 写产品方案与可观察的完成条件，必要时做最小 Demo。阶段 2 对比技术方案和长期维护成本。阶段 3 定稿完成定义和验收用例。每份文档均停等验收 |
| **人工审测试逻辑与评分** | 任务小步实现和自测。人审实际断言、数据与边界用例后才正式评分，影响判断的变更要复审。各功能通过率按算术平均得出总分，各功能和总分默认阈值均为 90%，还须通过必过用例 |
| **排障止损** | 一个假设加一次复验算一轮。同一问题连续两轮无可验证的进展，就暂停试改或原样重跑，把复现、日志和改动写入 `06-排障记录.md`。续接时沿用记录和恢复条件，详见 [排障规则](references/debugging.md) |
| **交付前人工体验** | 正式评分和代码审查通过后，用户或指定验收人亲自操作核心场景，确认通过后才按授权交付 |
| **检查点与文档备份** | 进入新阶段和修改代码前打检查点，文档改动留 `.bak`；随时说「回到阶段 N」 |
| **派活优先** | 核验首选和适用备选；均不可用时按你已选的方式处理，尚未选择时询问一次 |

## 安装

把整个 `vibe-code` 文件夹放到下面任一位置：

```
项目级（只在该项目生效）：
你的项目/.claude/skills/vibe-code/

全局（所有项目生效）：
C:\Users\<你的用户名>\.claude\skills\vibe-code/
```

新开 Claude Code 会话后，可明确要求从需求到交付的完整流程、续接进行中的流程、查询已交付的验收结果，或预览回到指定阶段的影响。


## 两个脚本怎么用

以下为 PowerShell 示例。将两个路径换成技能安装目录和项目根目录。Windows 可用 py -3 或 python，其他平台使用 python3 和对应的路径写法。

```powershell
$skillPath = 'C:/path/to/vibe-code'
$projectPath = 'C:/path/to/my-project'

# 已有 Git 仓库时，先检查原有改动
git -C $projectPath status --short

# 按阶段 0 核对或补齐适用项目规则后，只补缺少的文档，再创建真实基线
py -3 "$skillPath/scripts/init_vibe.py" --project $projectPath --type web --name "我的应用"
py -3 "$skillPath/scripts/checkpoint.py" --project $projectPath snap -m "阶段 0 基线"

# 从列表选实际编号，先看详情和回退计划
py -3 "$skillPath/scripts/checkpoint.py" --project $projectPath list
$checkpointId = Read-Host '输入要预览的检查点编号'
py -3 "$skillPath/scripts/checkpoint.py" --project $projectPath show $checkpointId
py -3 "$skillPath/scripts/checkpoint.py" --project $projectPath restore $checkpointId --dry-run
```

用户确认回退范围后，使用同一编号执行。

```powershell
py -3 "$skillPath/scripts/checkpoint.py" --project $projectPath restore $checkpointId --yes
```

### 检查点覆盖范围

- 在 Git 仓库根目录使用 Git 模式，保存已跟踪文件、未忽略的未跟踪文件和暂存状态。支持尚无首次提交的仓库。恢复文件和暂存状态时 HEAD 保持原位。遇到 intent-to-add、assume-unchanged 或 skip-worktree 暂存标记时，脚本会报告具体路径并停止。
- 文件模式覆盖常规文件和符号链接本身。跳过 Git 元数据、嵌套 Git 仓库及这些依赖或缓存目录：node_modules、.venv、venv、__pycache__、.pytest_cache、.mypy_cache、.ruff_cache。
- 两种模式均跳过项目根目录下整个 docs/vibe/，保留状态、门禁文档、文档备份和检查点历史。流程文档按 [文档回退步骤](references/fallback-rules.md) 单独恢复。Git 模式也跳过嵌套仓库和子模块。
- 新检查点在已知覆盖范围内恢复保存的内容和文件集合。回退默认只预览。确认计划后用 `--yes`。脚本在实际改动前保存安全检查点，已与目标一致时报告无需回退。
- 完整回退要求当前项目与检查点使用同一种模式。手工与旧版文件检查点只恢复保存过的文件。旧版 Git 检查点依赖原提交，且无法补回当时仅记录了摘要的未提交内容。

### 使用隔离 worktree

实现、测试及代码检查点都在当前代码根目录执行。切换后重读适用项目规则，确认能找到原项目的 `docs/vibe/state.md`。流程文档和状态仍写入原项目，状态会记录代码根目录与该目录下的快照编号。实现默认保留未提交改动，按任务提交需要事先授权。

## 生成的文件

阶段 0 核对适用的项目规则文件，例如 `AGENTS.md` 或 `CLAUDE.md`。流程产物保留在原项目：

```
docs/vibe/
├── state.md              ← 规则入口、进度、检查点、关键决策、回退和下一动作
├── 01-需求.md            ← 门禁 1
├── 02-技术栈.md          ← 门禁 2
├── 03-验收标准.md        ← 门禁 3
├── 04-任务清单.md
├── 05-评分报告.md        ← 人工审测试逻辑、验证得分和人工体验记录，按流程创建
├── 06-排障记录.md        ← 遇到问题时创建，记录尝试、暂停和恢复条件
└── checkpoints/          ← 此根目录的检查点索引与保存内容
```

## 一个典型会话长什么样

```
你：我想做个收集网摘的小工具，请按完整流程来。
agent：（阶段 0）核对 Git 和项目规则，把规则指向状态文件，记录基线检查点。
       （阶段 1）先确认一个问题：首版是给你自己在单台设备上用，还是给团队共享？
       产品方案成文后停在 01-需求.md，等你确认场景和完成条件。
       （阶段 2–3）分别提交技术方案和验收标准。说明维护成本，并写清必过用例。
       （阶段 4–5）拆任务、实现、自测，再请你审查实际测试逻辑和数据。
       （阶段 6）人审通过后评分。若结果为 76.25%，报告失败用例并等待你的决定。
       同一失败连续两轮无进展时，先整理复现、日志和已尝试的改动。
       （阶段 7–8）评分和代码审查通过后，请你在当前版本亲自保存一条网摘并重新打开核对。
       体验通过后，按你授权的方式交付。
```

## 注意事项

- **不同宿主的技能和工具可能不同**。派活前核验当前会话的技能与必需工具。若首选和适用备选均不可用，按你已选的方式处理，尚未选择时询问安装、自干或由你处理。
- **启动新流程需要明确的全流程信号**。单独修 bug、解释代码或执行现成计划，按对应任务处理。
- **保留验收文档和备份**。复查时按归档的文档版本和对应检查点核对。
