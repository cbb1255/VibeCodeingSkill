# 内置简版规则（用户选 B：自干）

> **什么时候读本文件**：用户在某阶段选了「B. 我用内置简版规则直接做」时；以及任何时候要做**回退操作**（"回到阶段 N"、撤销改动、恢复文档）之前。
> 用法：找到对应阶段的小节，照着步骤走。**每个自干阶段都必须在 `docs/vibe/state.md` 里标注「阶段 N 自干」**——这是硬要求，不是可选项。

## 自干前的三件事（每个阶段都一样）

1. **标注**：在 `state.md` 追加 `阶段 N 自干（记录候选技能不可用的原因及用户授权）`。
2. **打检查点**：在实际代码根目录用脚本打快照，把真实编号和根目录写进原项目的 state.md。
3. **沿用流程门禁**：三份文档、测试逻辑人工审查和交付前的亲自体验，都按 [主流程](../SKILL.md) 取得对应批准。

# 一、阶段：自干版最小可行做法

## 阶段 0：意图与续接（本来就自干）

按 [主流程阶段 0](../SKILL.md) 核对 Git 与项目规则。先落实适用规则及其状态入口，再建真实基线。续接时重读适用规则和原项目记录，沿用已确认的基线和等待事项。

## 阶段 1：需求追问（重点）

`grill-me` 和适用备选都不可用、用户已选择内置规则时，使用以下流程。

1. **先核对字段**：按 `references/doc-templates.md` 的必填字段整理用户已有信息，仅询问仍缺的字段。
2. **一次只问一个**：从「目标是什么、做给谁用」开始，每题给 **2–4 个具体可选项**，不要「是/否」。
3. **问的顺序**（照抄）：
   - 目标 → 使用者 → 核心场景（用户会怎么用它）→ 输入/输出 → 边界（什么情况不管）→ **明确不做什么** → 数据从哪来/存哪 → 失败时怎么办 → 非功能维度（按项目类型挑）。
4. **非功能按类型挑问**：CLI 工具问性能/错误提示；Web 问浏览器支持/响应式/鉴权；库问 API 稳定性/依赖最小化；脚本问幂等；数据处理问数据量级/精度；桌面或移动问平台/离线。**无关的写「不涉及」，不要留空**。
5. **每问一个问题就回填一个字段**，全部填满才算追问结束。
6. **写 `docs/vibe/01-需求.md`**（写之前先把旧版备份成 `.bak`，见回退速查），给出产品方案、关键用户路径和可观察的完成条件。交互存在关键不确定性时用最小 Demo 验证或沟通。落盘后**停**，请用户验收目标、场景、边界和完成条件。
7. 用户说「不对/再想想」→ 回第 2 步补问 → 改文档（改前再打一个 `.bak`）→ 重新验收。

> 自干时最容易犯的错：自己替用户假设答案然后一次问一堆。**必须一问一答**。

## 阶段 2：技术栈（本来就自干）

按 [主流程阶段 2](../SKILL.md) 写清技术方案、八项选型及备选理由，用长期维护成本比较可行方案。已有工程文件默认沿用并注明「沿用现有」，给出保留成本与改造取舍。写成 `02-技术栈.md` 后停等验收。

## 阶段 3：验收标准（本来就自干）

按 [主流程阶段 3](../SKILL.md) 将可观察的产品完成条件写成 `03-验收标准.md` 的正式完成定义。按模板列逐功能用例、必过项、阈值及获批例外，落盘后停等验收。测试逻辑的实际人工审查和使用者上手验收分别在后续门禁执行。

## 阶段 4：拆任务（本来就自干）

每个任务三件事：**改什么文件 / 做完怎么算完（可验证）/ 依赖哪个任务**；标出可并行任务，任务难以独立实现和验证时就再切；写进 `04-任务清单.md`（带编号）并更新 `state.md`。

## 阶段 5：计划执行（重点）

无 `executing-plans` / `subagent-driven-development` 时的自干流程。用户只要求验收已有实现时，定位对应任务后直接从第 4 步执行。

1. **动手前打检查点**。在 state.md 指定的代码根目录创建快照，记录根目录和真实编号。
2. **一个任务一轮**：从 `04-任务清单.md` 取**第一个未勾选**的任务，只做它。
3. **先读后改**：动某个文件前先读它，不要凭印象改。
4. **验证后判定完成**：执行任务清单指定的验收命令，按 SKILL.md 阶段 5 判定并记录结果。失败或受阻时保留任务为「进行中」，暂停提交、依赖任务及进入阶段 6，并按 [排障规则](debugging.md) 记录和处理当前问题。
5. **通过后勾选并留痕**：在原项目的 `04-任务清单.md` 标记完成，并更新 `state.md`。
6. **按授权处理改动**。默认保留未提交改动。若用户已明确授权按任务提交，仅提交已验证的本任务内容，先核对暂存区和文件范围，提交信息带任务编号。
7. **偏差就停**：发现需求不够用、或做着做着超范围 → 停下问用户，不许自己扩大范围。
8. 回到第 2 步，直到任务均通过。按 [测试逻辑审查](../SKILL.md) 提交实际测试逻辑或手动测试步骤，请用户或指定的人审查。把对当前版本的审批追加到 `05-评分报告.md` 后，才进入阶段 6。

> 自干时最容易犯的错：一口气改十几个文件然后一次性说「做完了」。每个任务各自留检查点并验证。

## 阶段 6：验证打分（本来就自干）

先按 SKILL.md 阶段 6 核对当前测试逻辑的人工批准及活动排障状态，再从代码根目录运行用例并按模板评分。在原项目的 `05-评分报告.md` 追加本轮结果。失败按 [排障规则](debugging.md) 处理，未通过时保留等待用户选择的门禁。用户选择收尾则记为「已收尾（未验收）」。

## 阶段 7：代码审查（重点）

无 `requesting-code-review` 时的自干流程：

1. 按下方「审查改动取证」检查从实现基线起的全部相关代码变更。
2. **按四类逐项审**（照表打勾，不要凭感觉）：
   - **对上需求**：每条改动能不能对上 `01-需求.md` 的某一项？对不上 = 超范围，记为阻断。
   - **对上验收**：`03-验收标准.md` 的 🔴 用例有没有被覆盖？有没有用例其实没真正验到？
   - **正确性**：错误处理、边界输入、空值、并发/重复执行、资源释放。
   - **可维护性**：命名、重复代码、硬编码路径/密钥、调试残留（`print`/`console.log`/`TODO`）。
3. **分级**：阻断（不满足需求、明显 bug、安全问题、测试没过）/ 非阻断（风格、优化建议）。
4. **阻断项回阶段 5 处理**。先按 [排障规则](debugging.md) 检查同一问题是否已到暂停条件，再按批准范围修复、重跑阶段 6 和审查。若测试逻辑变更，重新取得对当前版本的人工批准。
5. 非阻断项整理成清单交用户拍板，用户说不改就记进 `05-评分报告.md` 的遗留项。

> 自干审查的诚实提示：**自己审自己容易漏**。要主动跟用户说一句「这是自审，建议你或第三方再看一遍」，并把审查清单贴给用户核对。

### 审查改动取证

在 state.md 记录的代码根目录执行，并以该根目录对应的实现前快照为基线。

- Git 项目分别检查已提交、已暂存、未暂存和未跟踪的变更。下面各命令中的路径范围排除流程文档目录。空仓库没有已提交区间时，跳过第一条，仍检查其他三项。
```bash
git diff <实现基线commit>..HEAD -- . ':(exclude)docs/vibe/**'
git diff --cached -- . ':(exclude)docs/vibe/**'
git diff -- . ':(exclude)docs/vibe/**'
git ls-files --others --exclude-standard -- . ':(exclude)docs/vibe/**'
```
- 逐个读取未跟踪的相关文件。基线本来有未提交改动时，再对照基线快照的原始内容来区分既有改动和本流程的改动；必要时核对保存的暂存状态。若当前使用旧版脏 Git 检查点，明确记录历史资料缺失造成的审查限制。
- 无 Git 时将当前受管文件与实现前快照逐项比较，检查新增、修改、删除。旧版或手工快照的范围有限时，明确说明哪些内容没有基线证据。
- 把同样的证据交给外部审查技能。将只存在于用户本地的无关改动记录为背景，审查和交付范围按需求及任务清单确定。

## 阶段 8：交付

按 SKILL.md 阶段 8，先请用户或实际使用者亲自运行选定版本，体验核心场景，并把结果追加到 `05-评分报告.md` 的「人工体验验收」。待人工确认通过后再按授权交付。体验发现问题时按主流程记录和处理，用户选择结束时标为「已收尾（未验收）」。

用户选择保留改动时，汇报当前工作区、验收分数及遗留项。无 Git 时汇报本地文件路径。

用户授权 Git 交付时，按选定动作核对文件范围、已有暂存内容、工作区和目标分支。需要提交时只包含获授权的改动，处理 PR 或 tag 时仅执行获授权的远端操作。成功后在原项目的 state.md 归档。

# 二、回退操作速查（重点）

> 触发条件写在每一条前面。**先判断触发条件，再动手**，不要凭手感直接敲命令。

## A. 三份验收文档回退（触发：要改 01/02/03 任何一份之前；或用户要求恢复某个旧版本）

### 生成 `.bak`（每次改文档前**必做**）

1. 先确定序号：看目录里已有的 `NN-xxx.md.bak.*`，取**最大序号 + 1**（首次为 `.bak.1`）。
2. 从原项目根目录复制源文件，选择一个当前未用的备份编号。以下命令在目标已存在时会失败。
   ```powershell
   $source = Join-Path $PWD 'docs/vibe/01-需求.md'
   [System.IO.File]::Copy($source, "$source.bak.3", $false)
   ```
   ```bash
   (set -C; cat "docs/vibe/01-需求.md" > "docs/vibe/01-需求.md.bak.3")
   ```
3. 确认命令成功且备份内容完整，再修改原文。编号冲突时重新计算编号，使用新的路径。
4. 在 `state.md` 记一行：`改 01-需求.md，备份为 01-需求.md.bak.3，原因：<一句话>`。

### 恢复（触发：用户说"需求改回上一版 / 这个改动我不同意"）

1. **先列出可选版本**给用户看：文件名 + 备份时间 + 对应改动原因（从 `state.md` 查）。
2. 让用户选**恢复到第几号**，不要自己替他选。
3. 按上面的命令给当前版本生成一个新的 .bak。备份成功后，将用户确认的旧版复制回原路径。恢复时可覆盖原文，所选备份和其他 .bak 都保留。
4. 恢复后**重新走该阶段的门禁**（贴摘要、问用户验收），不能默认"恢复完就算过了"。

### 铁律

- **禁止删除任何 `.bak` 文件**，包括"没用了的旧备份"。它们是唯一的历史。
- 禁止直接覆盖 `.bak`（序号只增不减）。同一个序号被覆盖 = 历史丢失。
- 若某份文档从没打过 `.bak` 就已经被改坏了 → 只能靠 git（见 B）或快照（见 D）找回，如实告诉用户。

## B. 代码回退

1. 在原项目的 state.md 找到目标阶段对应的代码根目录与检查点编号。用同一个根目录执行 list 和 show。目录或编号找不到时先核对，不用其他 worktree 的同名编号代替。
2. 用脚本的 `restore` 预览计划，向用户展示新增、覆盖、删除以及暂存状态变化等影响。用户确认后，用 `--yes` 执行同一目标。实际恢复文件或暂存状态前，脚本会创建安全检查点。
3. 在原项目的状态中记录脚本的实际结果和代码根目录。报告「无需回退」时，记录「无变更」，安全检查点栏填「—」。脚本创建快照时，记录它给出的真实编号。失败时记录失败原因和工作区实际状态。
4. 老的干净 Git 检查点需要原提交仍可读取。老的脏 Git 检查点没有未提交内容，不能完整还原。避免将 Git 临时改动当作该旧快照的内容。
5. 用户明确要求撤销某个已提交变更时，可按授权处理 git revert，并核对提交范围。阶段回退优先使用检查点；它保存的代码状态也可以包含用户已暂存和尚未提交的改动。

## C. 没有 Git 或脚本不可用

有脚本时走文件模式。新文件快照覆盖受管文件集合，已保存文件可复原，目标快照之后新增的受管文件会在确认后移除。受管范围见 README。

脚本不可用时按 [状态格式](state-format.md) 记录手工检查点与受管文件副本。恢复手工和旧版文件快照是逐项覆盖，只恢复已保存的文件。先核对副本完整性，列出覆盖范围，备份当前内容并取得授权。

## D. 回到阶段 N

1. 对照两个根目录列出影响面。文档查看版本和 .bak，代码查看阶段检查点和 restore 预览，测试查看评分报告轮次。
2. 让用户选择全退、只退文档、只退代码或保留代码重写文档，并确认具体版本和作用范围。
3. 先预检代码和文档备份。选全退时先执行已确认的代码回退，再恢复文档。文档回退遵循 A 节，当前版本恢复前另存备份；如涉及 04/05，也先保留当前内容和历史，05 的过往评分保留并标注对应版本。
4. 执行后在原项目的 `state.md` 追加实际结果，按实际恢复范围更新进度及受影响的验收状态。仅代码回退且脚本报告无变更时沿用当前状态。排障记录及相同问题的证据和计数继续保留。记录已创建的快照和文档备份。

# 三、自干阶段标记（硬要求）

| 情况 | `state.md` 必须有的字样 |
|---|---|
| 阶段 1 自干 | `阶段 1 自干（记录候选技能不可用的原因及用户授权）` |
| 阶段 5 自干 | `阶段 5 自干（技能 executing-plans 缺失，用户选 B）` |
| 阶段 7 自干 | `阶段 7 自干（技能 requesting-code-review 缺失，用户选 B）` |
| 阶段 8 自干 | `阶段 8 自干（技能 finishing-a-development-branch 缺失，用户选 B）` |

- 阶段 2/3/4/6 本来就无技能，**不需要**标「自干」（它们不在派活清单里），但仍要留阶段切换记录。
- 用户选 C（自己来）时写 `阶段 N 用户自做`；用户选 A（安装）成功后写 `阶段 N 派活：<技能名>`。
- 交付摘要里要能一眼看出哪些阶段是自干出来的，方便用户判断质量风险。
