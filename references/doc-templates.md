# 文档模板集

> 用法：写阶段 1 / 2 / 3 / 4 的文档，或准备测试逻辑人工审查、评分、人工体验验收时，**先读本文件对应小节**。
> 每份模板都分三部分：**完整模板代码块**（可直接复制）+ **必填字段说明** + **填写要点 / 常见错误**。
> 占位约定：`___` 表示必须由用户确认的内容，`[方括号]` 表示示例或可选说明，填空后要删掉占位符号。

| 阶段 | 产出文件 | 对应小节 | 门禁 |
|---|---|---|---|
| 1 | `docs/vibe/01-需求.md` | 一 | 🔴 停 |
| 2 | `docs/vibe/02-技术栈.md` | 二 | 🔴 停 |
| 3 | `docs/vibe/03-验收标准.md` | 三 | 🔴 停 |
| 4 | `docs/vibe/04-任务清单.md` | 四 | — |
| 5 → 6 | `docs/vibe/05-评分报告.md` 的人工审查记录 | 五 | 人工通过后才正式评分 |
| 6 | `docs/vibe/05-评分报告.md` 的评分轮次 | 五 | 🟡 每轮不达标都停 |
| 7 → 8 | `docs/vibe/05-评分报告.md` 的人工体验验收记录 | 五 | 人工体验通过后才交付 |

> **改门禁文档前必做备份**：01/02/03 这三份门禁文档改写前都应备份成 `NN-xxx.md.bak.<序号>`。
> 序号规则：首次为 `.bak.1`，之后取目录中已有 `.bak.*` 的**最大序号 + 1**；**只增不减，禁止覆盖或删除任何 `.bak`**。
> 具体命令（Windows / Linux）见 `fallback-rules.md`「回退操作速查 · A 节」。

## 一、01-需求.md（需求文档）

```markdown
# 需求文档 — ___[项目名]

- 项目类型：___[CLI工具 / Web应用 / 库 / 脚本 / 数据处理 / 桌面或移动]
- 文档版本：v1 | 最后更新：____-__-__ | 状态：待验收 / 已验收

## 1. 一句话目标
___[用一句话说清「给谁、解决什么、做成什么样」，不许出现「优化」「赋能」这类空词]

## 2. 目标用户 / 使用者
- 主要用户：___[谁，什么角色]
- 技术水平：___[完全不懂技术 / 会敲命令 / 是开发者]
- 使用频率：___[每天 / 每周 / 一次性]
- 使用环境：___[自己的电脑 / 服务器 / 浏览器 / 手机]

## 3. 核心使用场景（3–6 条）
| 编号 | 谁 | 在什么情况下 | 做什么 | 期望结果 |
|---|---|---|---|---|
| S1 | ___ | ___ | ___ | ___ |
| S2 | ___ | ___ | ___ | ___ |
| S3 | ___ | ___ | ___ | ___ |

### 产品方案
___[写清核心用户路径，从入口、关键操作到用户看到的结果。交互有待确认时，附最小 Demo 或原型链接，并标出要验证的操作。]

### 阶段 1 的完成条件草案
___[引用核心场景编号，写用户实际操作和可观察的结果。例：S1 导出三行记录后，CSV 保留三条记录的列名和顺序。用例、判定和阈值在阶段 3 确认。]

## 4. 输入与输出
| 类型 | 内容 | 格式 / 示例 |
|---|---|---|
| 输入 | ___[要处理的数据 / 文件 / 请求 / 参数] | ___ |
| 输出 | ___[产出什么：文件 / 屏幕输出 / 接口返回] | ___ |
| 错误输出 | ___[出错时给什么信息] | ___ |

## 5. 边界与约束
- 规模上限：___[数据量 / 并发数 / 文件大小 / 请求频率]
- 时间约束：___[多久要跑完 / 截止日期]
- 环境约束：___[必须离线 / 必须能装在旧机器 / 必须免登录]
- 合规与许可：___[不能说不出：私有数据能否外传、依赖许可要求，没有就写「无」]

## 6. 明确不做的事（最重要）
1. ___[例：不做用户注册和登录，只有本地单用户]
2. ___[例：不接第三方支付]
3. ___[例：不处理 10MB 以上的文件]
4. ___[例：不做 Windows 之外的平台]
> 实现阶段一旦有人提出做这几件事，先停下问用户，不许自己扩大范围。

## 7. 非功能需求（按项目类型填，不相关写「不涉及」）
| 维度 | 本项目要不要 | 要求（可量化） |
|---|---|---|
| 性能 | ___ | ___[例：1000 行 CSV 3 秒内出结果] |
| 安全 | ___ | ___[例：不把密钥写进代码、日志不打隐私字段] |
| 并发 | ___ | ___[例：单线程即可] |
| 多平台 | ___ | ___[例：Win10 + macOS 都要能跑] |
| 离线可用 | ___ | ___[例：完全离线] |
| 隐私 | ___ | ___[例：数据不离开本机] |
| 可维护性 | ___ | ___[例：单文件 300 行内，不引框架] |

## 8. 待定项（不许空着）
| 编号 | 待定内容 | 为什么还没定 | 什么时候必须定 | 暂定做法 |
|---|---|---|---|---|
| Q1 | ___ | ___ | ___[例：阶段 3 之前] | ___ |
| Q2 | ___ | ___ | ___ | ___ |
```

### 必填字段说明

| 字段 | 为什么必须有 |
|---|---|
| 一句话目标 | 全文其他内容都要能对上这一句；对不上就说明写偏了 |
| 目标用户 | 决定交互方式、文档写法、默认值；用户群不同产品形态完全不同 |
| 核心使用场景 3–6 条 | 少于 3 条说明需求没想清；多于 6 条要拆成两个项目或分两期 |
| 产品方案 | 用户可沿核心路径核对产品行为。交互仍有不确定时，用最小 Demo 或原型验证。 |
| 完成条件草案 | 核心场景各有可观察的结果，作为阶段 3 验收用例的依据 |
| 输入与输出 | 这是验收用例的素材来源，缺了阶段 3 写不出来 |
| 边界与约束 | 判断「做到哪算够」，也是排期依据 |
| 明确不做的事 | **防止范围膨胀**，是阶段 5「偏离需求就停」的对照表 |
| 非功能需求 | 逐类型挑问，本类不相关就显式写「不涉及」，不能跳过 |
| 待定项 | 把「还没定」也写下来，比假装定好了安全；空着等于隐瞒风险 |

**非功能维度按项目类型的问法**

| 项目类型 | 优先问 | 一般不问（写「不涉及」） |
|---|---|---|
| CLI 工具 | 启动速度、无网络可用、跨平台、帮助信息可读性 | 并发、前端性能 |
| Web 应用 | 首屏时间、并发、鉴权与安全、浏览器兼容 | 安装包体积 |
| 库 | 向下兼容、依赖数量、类型标注、线程安全 | 部署方式、UI |
| 脚本 | 幂等、可重复跑、出错能否恢复、日志 | 并发、扩展性 |
| 数据处理 | 数据量上限、内存占用、精度、乱序/脏数据处理 | UI、交互 |
| 桌面或移动 | 安装包体积、离线、系统权限、内存 | 服务端并发 |

### 填写要点 / 常见错误

- ✅ 每个场景写成「谁 → 什么情况 → 做什么 → 期望结果」四段，缺一段就补问。
- ✅ 「明确不做的事」至少写 3 条。只有 1 条说明还没跟用户对过边界。
- ✅ 拿不准就问一次一个问题，不要在一段里塞三个问题。
- ❌ **空话**：「高效地处理数据」「体验流畅」——不可验证，必须换成数字。
- ❌ **需求写成方案**：不要写「用 SQLite 存」，那是阶段 2 的事。
- ❌ **非功能需求留空**：留空 ≠ 不涉及，必须显式写「不涉及」。
- ❌ **待定项写「暂无」**：只要还没定，就要写清「什么时候必须定」。
- ❌ 场景只写「用户可以使用 X」，没写谁、什么时候、要什么结果。

### 必填字段说明

| 字段 | 填什么 |
|---|---|
| 语言 | 具体到主版本号，不写「Python」 |
| 框架 | 没有框架就显式写「无，原因是…」，不能留空 |
| 运行环境与版本 | 跑在哪、最低版本、装什么运行时 |
| 依赖清单 | 名称 + 版本 + 用途 + 为什么非它不可，四项齐全 |
| 目录结构约定 | 用代码块画出，并写出「一个文件只做一件事」这类硬约定 |
| 数据存储 | 存哪、什么格式、备份怎么办 |
| 外部服务 | 名字、用途、是否需要密钥、不联网怎么办 |
| 部署方式 | 用户最终怎么拿到并跑起来，具体到命令 |
| 维护成本 | 选择与项目相关的依赖升级、排障、测试、部署与回滚、交接等代价，比较拟选方案和现实备选（已有工程可用沿用作对照）。缺少证据时写明待核实项和验证方式。 |
| 技术方案 | 看得出关键组件如何协作，或从入口到结果的数据流与接口边界 |

**三列法是硬要求**：`选了什么 / 为什么选它 / 排除了哪些备选及原因`。第三列是将来改主意的唯一依据，写「没有备选」等于没做选型。

### 填写要点 / 常见错误

- ✅ 先问用户倾向，再把候选的利弊摆出来让他选；不要直接宣布结论。
- ✅ 「为什么」要能站住：「我最熟」也是好理由，但要写出来。
- ✅ 已有工程**默认沿用**，只补缺的，改动项在「沿用的现有配置」里标清影响。
- ✅ 用维护任务、所需步骤或现有数据说明代价。没有数据时可定性判断并记录依据。
- ❌ **只写结论不写理由**：只写「用 FastAPI」，将来没人知道为什么不能换。
- ❌ **排除了哪些备选**写成「都差不多」——必须说出具体差在哪。
- ❌ 依赖写「最新版」：必须钉版本，否则明天就装不上。
- ❌ 部署方式写「部署到云端」：要写清具体命令或平台步骤。
- ❌ 顺手引入新依赖不声张：加依赖是不可逆操作，必须先问用户。

## 三、03-验收标准.md（验收标准文档）

```markdown
# 验收标准 — ___[项目名]

- 文档版本：v1 | 最后更新：____-__-__ | 状态：待验收 / 已验收
- 对应已验收的需求版本：01-需求.md v__
- 及格线：90%（逐项可改，见第 4 节）

## 完成定义
- 核心场景与观察结果：___[引用 01 的场景编号，列出用户能看到的结果及验证用例编号]
- 验收条件：按本文版本的必过用例、功能及总分阈值和有效例外判定。
- 验收证据：实际测试逻辑经人工审查通过，正式评分引用审查记录。
- 交付条件：正式评分通过，代码审查的阻断问题处理完毕，用户或其指定的人亲自体验核心场景并确认通过。

## 1. 测试集来源
- 来源类型：___[公开测试集 / 用户提供 / 总控自拟]
- 具体来源：
  | 功能 | 用例来源 | 出处链接 | 是否完整采用 | 增减说明 |
  |---|---|---|---|---|
  | ___ | ___[例：某开源项目测试用例] | ___[https://...] | 完整采用 / 采 8 条改了 2 条 | ___ |
  | ___ | 自拟 | — | — | 依据 01-需求.md 场景 S1–S3 |
- 来路不明、无法给出处的外部测试集，**不得采用**。

## 2. 测试用例表
### 功能 F1：___[功能名，与 01-需求.md 的场景对应]
| 用例编号 | 输入或操作 | 预期结果 | 优先级 |
|---|---|---|---|
| F1-01 | ___ | ___ | 🔴 必过 |
| F1-02 | ___ | ___ | 🔴 必过 |
| F1-03 | ___ | ___ | 🟡 加分 |

### 功能 F2：___[功能名]
| 用例编号 | 输入或操作 | 预期结果 | 优先级 |
|---|---|---|---|
| F2-01 | ___ | ___ | 🔴 必过 |
| F2-02 | ___ | ___ | 🟡 加分 |

> 每个功能至少 3 条用例，🔴 与 🟡 都要有。只写一条「能用」不算测试用例。

## 3. 评分方式
- 每个功能得分 = 该功能**实际通过的用例数 ÷ 总用例数 × 100**。未运行、跳过和受阻的用例单独列出，仅实际通过的用例计入分子。
- 总分 = 各功能得分的算术平均，每个功能等权。报告展示可保留两位小数，判定使用未舍入分数。
- 单条用例的判定：___[例：输出与预期完全一致，最多允许 ___ 秒误差]
- 验收通过须同时达到所有功能及格线与总分及格线，且全部 🔴 必过用例通过。明确批准的例外仅豁免指定条件，原始结果照实保留。

## 4. 及格线与逐项确认
| 功能 | 默认及格线 | 用户确认后及格线 | 确认结果 |
|---|---|---|---|
| F1 | 90% | ___ | ___[已确认 / 用户改为 __%] |
| F2 | 90% | ___ | ___ |
| 总分 | 90% | ___ | ___ |
> 探索性项目可放宽到 70%，生产工具建议 100%。改及格线必须记下用户原话。

## 5. 例外约定（用户说不达标也可以时，原样记录）
- 用户原话：___[无例外时填「无」]
- 适用范围：___[被豁免的用例编号或分数阈值]
- 适用条件或轮次：___
- 记录时间：____-__-__，确认人：用户
> 批准后如实记录分数及失败用例。仅指定范围可以按例外交付。
```

### 必填字段说明

| 区块 | 为什么必须有 |
|---|---|
| 完成定义及需求版本 | 把核心场景、可观察结果、验收判定与交付条件对齐到同一版本 |
| 测试集来源 | 避免用来路不明的用例撑起验收；外部来源必须能点开核对 |
| 是否完整采用 | 说明「照抄了哪些、自己改了哪些」，防止偷偷降低难度 |
| 逐功能用例表 | 阶段 6 就照这张表跑，一条都不能临时加 |
| 优先级 | 🔴 决定能不能交付，🟡 决定做得多好 |
| 评分方式 | 公式写死，避免每轮用不同算法得出不同分数 |
| 及格线逐项确认 | 默认 90%，每个功能都要单独问过并记结果 |
| 例外约定 | 记录用户原话、具体豁免条件和适用范围 |

### 填写要点 / 常见错误

- ✅ 用例格式固定为「输入或操作 → 预期结果」，预期结果要**可观察**（能看到输出、文件、退出码）。
- ✅ 先上网找该领域公开测试集或业界 checklist；找不到再问用户；都没有才自拟并标注「自拟」。
- ✅ 用例编号与功能绑定（F1-01），阶段 6 出错时能直接回指需求场景。
- ✅ 每个功能写 3–8 条，覆盖正常路径 + 边界 + 出错路径各至少一条。
- ❌ **预期结果模糊**：「能正常处理」不可测，要写「输出 3 行，第一行为 xxx」。
- ❌ **用例跟着实现走**：写代码后回头改用例凑分数，属于作弊，必须回阶段 3 重新验收。
- ❌ **只用 🔴 不用 🟡**：没有加分项就无法体现「做得好不好」。
- ❌ **及格线一刀切不问**：默认 90% 要逐项确认，用户改了必须记录。
- ❌ 例外只写「用户说可以」：记录原话和明确豁免范围。

### 必填字段说明

| 字段 | 判定标准 |
|---|---|
| 任务编号 | T1、T2 递增，不复用、不跳号 |
| 改什么文件 | 写具体路径，不写「后端相关」；新建要注明「新建」 |

「覆盖对照」表不进模板也算漏项：它保证阶段 3 的每条 🔴 用例都有人做。

### 填写要点 / 常见错误

- ✅ 每个任务保留独立的检查点和验收证据。用户已授权按任务提交时，在提交信息带上任务编号。
- ✅ 「算完」写成可执行验证：`pytest tests/test_x.py -k y` 通过、命令输出含某行、文件生成且大小在其范围。
- ✅ 并行任务必须是**动的文件不重叠**的，否则还是排成串行。
- ✅ 每完成一个任务立刻回来把状态改成「完成」，别攒到最后一起改。
- ❌ **任务太大**：「实现整个后端」——无法验证、无法回退，要拆。
- ❌ **算完标准不可验证**：「代码质量好」「功能基本实现」，这种写法等于没有验收。
- ❌ **依赖写空**：漏写依赖会导致阶段 5 乱序执行、反复返工。
- ❌ **用状态玩文字游戏**：写「差不多完成」「90%」——只有三个合法值。
- ❌ 任务里偷偷加需求文档没有的功能：那要先回阶段 1 补文档。

### 填写要点 / 常见错误

- ✅ 每轮报告都要跟 `04-任务清单.md` 和 `state.md` 对齐，让用户能看到「这轮改了什么 → 分数动了多少」。
- ✅ 失败用例要**按 🔴 优先级排序**：必过用例失败优先于加分用例。

- ❌ **只报总分不报失败清单**：只写「85%」用户没法改。

- ❌ **覆盖上一轮报告**：历史轮次要保留，用于看趋势。
- ❌ 一轮跑完不更新 `state.md`：阶段 6 的结论必须留痕。
