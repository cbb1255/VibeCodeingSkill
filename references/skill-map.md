# 阶段 → 技能映射表

> **什么时候读本文件**：每次要「派活」之前（阶段 1、5、7、8 的开工瞬间），先查本表确认技能名，再决定派给谁。
> 派活前核验候选技能及其必需工具在当前会话是否可用（见文末「技能可用性」）。

## 总原则

1. 总控只做四件事：**判断阶段、守门、成文、拆任务**。凡是表里列了技能的阶段，不要自己埋头做。
2. 派活前必须先备齐「派它之前必须准备好什么输入」，输入不全就派出去 = 技能会自己乱猜。
3. 拿到的产出**先验一遍再定「阶段完成」**，技能说做完了不等于做完。
4. 首选不可用时核验适用的备选。没有可用候选时，按 SKILL.md「派活降级规则」处理用户已有的选择，或询问一次。
5. 下表列出候选技能。派活前按文末规则核验，结果写进 `state.md`。

> `grill-me` 由用户装在 `~/.claude/skills/`（Claude Code 侧，已确认安装过）；
> 其余七个（`brainstorming`、`writing-plans`、`executing-plans`、`subagent-driven-development`、
> `using-git-worktrees`、`requesting-code-review`、`finishing-a-development-branch`）
> 来自 Harness 会话的固定技能目录，**不代表 vibe-code 真正运行时（Claude Code / Cowork）里一定存在**，
> 反过来 Harness 会话里也可能没有 `grill-me`。本表只回答「这个阶段应该有个做什么的技能」；
> 「它此刻能否使用」，每次派活前都要按文末「技能可用性」，
> 从**当前会话注入的可用技能清单**查找，再核验工具和约束。

> 与本流程无关的技能（`interview-coach`、`office` 系列、`archify`、`book-to-skill`、`reverse-engineer-anything`、`orca-*` 等）**不要**往这些阶段里硬塞。

### 派活前的 5 步检查（每次派活都走一遍）

1. **阶段对不对**：现在这个阶段真的需要派活吗？（2/3/4/6 不许派）
2. **技能能不能用**：按文末「技能可用性」核验，写清用的是精确名还是近似名。
3. **输入齐不齐**：对照该技能小节的「派之前必须准备好」，缺一项就补，补不了就问用户。
4. **边界讲没讲**：派活时把「只做这一个任务」「不许扩大范围」「偏离需求就停」写进指令里。
5. **回来怎么验**：先想好「它交回来的什么东西能证明做完了」，再看产出。

## 技能逐个小节

### `grill-me` — 连环追问设计/需求

- **负责什么**：一次一问、每题给具体选项，把模糊想法问成有边界的需求；通常还会顺带逼出「不做什么」。
- **什么时候派给它**：阶段 1 仍需访谈时优先选用。派活前确认实际版本能使用要求的提问工具。如果安装版要求 `AskUserQuestion` 而当前会话没有该工具，将它视为不可用。
- **派之前必须准备好**：① 用户原始一句话需求（原样贴，别自己润色）；② 项目现状摘要（目录结构、已有技术栈，自己查到的）；③ 项目类型（CLI / Web / 库 / 脚本 / 数据处理 / 桌面、移动）；④ `references/doc-templates.md` 里「需求文档必填字段」清单，让技能知道要问到什么程度。
- **产出**：问答记录（对话形式），**不是** 成品文档。
- **它不能解决什么（总控补）**：① 按模板把问答整理成 `01-需求.md`；② 逐项对照必填字段查漏，缺的回去补问；③ 非功能需求按项目类型筛选，无关的写「不涉及」；④ 落盘后做门禁、贴摘要、等用户验收；⑤ 改文档前打 `.bak`。
- **备选 `brainstorming`**：首选不可用时，核验当前版本能否只做一个问题一个问题的需求探索，提供具体选项，并把结果交回总控。若它要求跳过选项、另走审批门禁、产出额外方案文档或进入实现，本阶段视为不适用。核验通过后只接手需求访谈，文档成文和验收仍由总控完成。

### `writing-plans` — 有 spec 后写多步实现计划

- **负责什么**：把已有 spec/需求转换成一份分步、可执行的实现计划（步骤顺序、依赖、检查点）。
- **什么时候派给它**：阶段 4 拆任务时，如果任务粒度粗、互相依赖复杂，或你不确定怎么排序，可借用它的计划结构。**不是必派**。
- **派之前必须准备好**：已验收的 `01-需求.md` + `02-技术栈.md`（最好还有 `03-验收标准.md`）。没有 spec 就派给它，它只能瞎编。
- **产出**：多步实现计划（可能落成文档），但**格式不等于我们的 `04-任务清单.md`**。
- **它不能解决什么（总控补）**：① 每个任务改成三要素格式：改什么文件 / 做完怎么算完（可验证）/ 依赖哪个任务；② 标出可并行任务；③ 写进 `docs/vibe/04-任务清单.md` 并更新 `state.md`；④ 确保每个任务可独立验证并有自己的检查点。

### `executing-plans` — 执行已写好的计划，带审查检查点

- **负责什么**：按计划逐步实现，中途设审查检查点，边做边汇报。
- **什么时候派给它**：阶段 5 开工、检查点已打、任务清单已定之后；**默认首选**。
- **派之前必须准备好**：① 已验收的 01/02/03 三份文档；② `04-任务清单.md`（带编号）；③ 当前代码根目录及该目录下的快照编号；④ 适用项目规则、原项目 `state.md` 路径、限定的任务和提交授权范围。
- **产出**：代码改动 + 进度汇报。
- **它不能解决什么（总控补）**：① 按 SKILL.md 阶段 5 核验任务，并在原项目更新任务清单和状态；② 验证通过后默认保留未提交改动，按任务提交须有用户授权；③ 判断需求偏差并叫停；④ 阶段 6 的打分由总控负责。
- **备选 `subagent-driven-development`**：任务之间**互相独立**（可并行、不共享文件）时用它，用子代理分头跑。任务强耦合、要频繁改同一批文件时别用，会互相踩。
- **前置 `using-git-worktrees`**：用户要求隔离、或当前工作区不适合直接动工（有别的未完成改动）时，阶段 5 开工前先派它建隔离工作区，再派执行类技能。

### `subagent-driven-development` — 用子代理执行独立任务

- **负责什么**：把独立任务分给子代理并行执行，汇总结果。
- **什么时候派给它**：阶段 5，且任务清单里明确标了「可并行」的那批任务。
- **派之前必须准备好**：任务间依赖图（谁依赖谁）、文件写入边界（每个子任务只能碰哪些文件）、每个任务的验收方式。
- **产出**：各子任务的分支/改动 + 汇总说明。
- **它不能解决什么（总控补）**：① 冲突检查（两个子代理改了同一个文件必须由总控发现并处理）；② 合并顺序；③ 核对暂存区并在授权范围内提交；④ 你仍要自己确认每个子任务真的可验证通过。

### `requesting-code-review` — 完成任务/合并前请审查

- **负责什么**：对已完成改动做代码审查，输出问题清单（阻断 / 非阻断）。
- **什么时候派给它**：阶段 7 开始时。
- **派之前必须准备好**：① 需求文档和验收标准（没有它们，审查只能看代码风格，看不了「是否满足需求」）；② 当前代码根目录、同一根目录的实现基线和完整变更证据（Git 中含已提交、暂存、未暂存、未跟踪，文件模式下含新增、修改、删除）；③ 当前测试和评分结果。
- **产出**：审查结论清单。
- **它不能解决什么（总控补）**：① 把问题分成「阻断 → 必须回阶段 5 修」和「非阻断 → 给用户拍板」；② 判断何时可以退出审查循环；③ 它**不跑**验收测试集，分数仍由阶段 6 出。

### `finishing-a-development-branch` — 实现完成、测试通过后决定如何集成

- **负责什么**：验收和审查结束后，执行用户确认的 Git 交付方式。
- **什么时候派给它**：阶段 8 的人工体验通过后，且用户明确授权了 Git 交付动作。保留本地改动则由总控按阶段 8 收尾。
- **派之前必须准备好**：① 用户明确授权的交付动作、文件和暂存范围；② 评分、代码审查和人工体验通过的证据及适用例外；③ 当前代码根目录、分支及目标。
- **产出**：提交/PR/tag 等交付动作的结果。
- **它不能解决什么（总控补）**：① 核对授权及具体操作；② 按实际结果更新原项目的流程状态；③ 写交付摘要（做了什么、验收分数、遗留项）。
- **绝对不能做**：用户没明确回答就把「如何集成」的选择权交给它——它会替你选，而这一步必须用户拍板。

### `using-git-worktrees` — 隔离工作区

- **负责什么**：建一个与当前工作区隔离的目录来干活。
- **什么时候派给它**：阶段 5 开工前，用户要求隔离 / 工作区脏且有别的活儿 / 想并行对比方案时。
- **派之前必须准备好**：仓库根路径、新分支名、基线 commit。
- **产出**：一个可工作的隔离目录路径。
- **它不能解决什么（总控补）**：① 把新路径和分支写入原项目的 state.md，在新路径上确认基线并创建真实快照；② 实现、测试和代码检查点使用新路径，原项目保留流程文档与备份；③ 阶段 8 按用户授权集成交付并处理仍需保留的目录。

## 明确不覆盖的阶段（必须总控自己做）

以下三件事**没有现成技能**，找也找不到。不要浪费时间找，也不要假装派过活。

### 1. 技术栈选型（阶段 2）

- **为什么没技能**：选型依赖这个项目的特殊约束（用户团队会不会、现有工程是否沿用、部署环境、离线要求），是**判断**不是**执行**，通用技能没法替你拍板。
- **总控怎么自干**：先问用户倾向（一次一问）→ 答不上来就给 2–3 个候选 + 利弊让用户选 → 按固定八字段写全 → **每项都写「为什么选它」和「排除了哪些备选」** → 已有工程文件默认沿用并注明。

### 2. 验收测试集编写（阶段 3）

- **为什么没技能**：验收测试集是**这个项目独有**的东西，通用技能产不出；而它的质量直接决定后面打分的可信度，外包出去等于把门禁交给别人。
- **总控怎么自干**：按需求逐功能列 `输入/操作 → 预期结果` 用例（🔴 必过 / 🟡 加分）→ 按「先上网找公开测试集 → 问用户有无现成 → 自拟」三档取来源，外部来源必附链接和采用范围 → 写各功能通过率和等权平均总分 → 确认各功能与总分阈值及必过用例 → 例外须记录原话、豁免范围及适用条件。

### 3. 测试集打分（阶段 6）

- **为什么没技能**：打分 = 逐条跑 `03-验收标准.md` 并如实计数。这件事一旦交给「帮忙的技能」，它天然倾向于报告通过，**门禁就失效了**。
- **总控怎么自干**：逐条跑并记录实际结果。在原项目追加评分报告，按已验收的阈值、必过用例和例外判定。未通过则等待用户选择后续动作。

> 补充：阶段 0（意图续接）和阶段 4（拆任务）也没有对口技能。阶段 4 只在需要排版参考时借用 `writing-plans` 的结构，拆法和粒度仍是总控定。

## 技能可用性

**禁止**凭印象假设「应该有这个技能」。按下面顺序确认：

1. **看当前会话的可用技能清单**。列表出现技能名称，说明可尝试加载。确认能够加载正文，并核验必需工具和当前阶段约束后才派活。
2. **名字不完全一致时按语义匹配，但只接受唯一匹配**。比如清单里是 `requesting-code-review`，就派这个精确名字，不要写成 `code-review`。清单里只有 `xxx-advanced` 而你要 `xxx` 时，视为**不完全一致**：可以试，但要告诉用户「我用的是近似的 xxx-advanced」。
3. 清单里没有、正文加载失败、缺少必需工具或无法满足本阶段约束时，记录原因，继续核验适用的备选。
4. 用户说明已安装或给出技能路径时，按当前会话能否加载正文和使用必需工具核验。用户已确认某技能不可用时，沿用结论，避免重复询问。
5. 没有可用候选时按 SKILL.md「派活降级规则」处理。用户已经明确选择内置规则、自己处理或安装路径时，沿用选择并遵守实际动作所需的授权。
6. 「装」「不装」这件事**只能用户说了算**：不要自行下载安装；用户选 A 时，先告知要装什么、从哪装、可能的影响，得到明确同意再动手。

### 判定结果往哪记

- 在 `docs/vibe/state.md` 的当前阶段记录使用的候选技能，或不可用原因及用户选定的处理方式。
- 走「自干」时，**必须**同时标注「阶段 N 自干」（硬要求，详见 `fallback-rules.md`）。

## 几个典型组合（照抄可用）

| 场景 | 派活顺序 | 说明 |
|---|---|---|
| 从零做一个小 CLI 工具 | `grill-me` → 自干 2/3/4 → `executing-plans` → 自干 6 → `requesting-code-review` → `finishing-a-development-branch` | 理想全技能路径（前提：每个技能都核验存在） |
| 已有仓库，只想加一个大功能 | 自干 0（先查现状）→ `grill-me` → 自干 2（标注「沿用现有」）→ 自干 3/4 → `using-git-worktrees` → `executing-plans` → 自干 6 → `requesting-code-review` → `finishing-a-development-branch` | 阶段 2 基本是沿用，重点在隔离工作区 |
| 需求多、任务相互独立，想快点做完 | `grill-me` → 自干 2/3 → 自干 4（标出可并行）→ `using-git-worktrees` → `subagent-driven-development` → 自干 6 → `requesting-code-review` → `finishing-a-development-branch` | 只有任务真的不共享文件才用并行 |
| 用户还需澄清需求，且首选不可用 | 核验 `brainstorming` → 收敛成需求字段 → 按阶段 1 的规则成文与验收 | 备选满足本阶段约束才可使用 |
